# 学习性源码审计计划（Agent 友好版）

**目的**：带着四个关键疑问，深入 Sub2API 源码，验证第一阶段初判结论，为第二阶段正式审计建立准确的技术认知。
**模式**：Agent 独立执行，读取 → 分析 → 输出纪要；大龙确认后进入第二阶段。
**产出**：每个问题一份审计纪要，共 4 份。

---

## 执行指令

对以下 4 个问题**并行**执行源码追踪，每个问题产出一份审计纪要。

追踪时：
1. 先用 grep 定位精确行号，再写入纪要
2. 不确定的地方必须定位到文件和行号，不得猜测
3. 如两个问题涉及同一文件，后者纪要中标注"此文件已在问题 X 中分析"

## 问题一：渠道概念到底是怎么实现的？

### 核心疑问
Sub2API 的"账号 (Account)" 究竟是如何同时扮演"渠道"角色的？它的 `ChannelMonitor` 表如果不是渠道，那它的路由逻辑是如何选择上游的？

### 源码追踪路径

| 步骤 | 追踪文件 | 要回答的问题 |
|------|---------|-------------|
| 1 | `ent/schema/account.go` | `Account` 有哪些关键字段？`Platform`、`Type`、`APIKey` 是如何存储的？ |
| 2 | `ent/schema/channel_monitor.go` | `ChannelMonitor` 表的结构是什么？它关联的是 `Account` 还是其他？ |
| 3 | `handler/gateway_handler.go` → `SelectAccount` | 关键！在接收到用户 API 请求后，是如何选择一个可用的 `Account` 来转发请求的？是按 `Platform` 匹配？优先级如何定义？ |
| 4 | `handler/admin/account_handler.go` | 管理员是如何创建和配置一个 `Account` 的？需要填写哪些参数？ |

### 验证目标
- [ ] 确认 `Account` 确实承载了"渠道"的角色，它定义了 `BaseURL` 和 `APIKey`
- [ ] 确认 `ChannelMonitor` 只是一个对 `Account` 的**健康检查配置**，不是流量入口
- [ ] 理解路由选择 (`SelectAccount`) 的核心逻辑：是轮询、随机、还是基于权重/优先级？

## 问题二：订阅粒度为什么不同？Sub2API 是怎么做的？

### 核心疑问
Sub2API 的订阅 (`user_subscriptions`) 是如何与用户和分组绑定的？当一个 Key 发起请求时，它的订阅配额是怎么被检查和扣减的？

### 源码追踪路径

| 步骤 | 追踪文件 | 要回答的问题 |
|------|---------|-------------|
| 1 | `ent/schema/user_subscription.go` | 这张表有哪些字段？有没有 `status`、`provider_id` 之类的字段？ |
| 2 | `ent/schema/subscription_plan.go` | 套餐 (`Plan`) 是如何定义的？有没有按供应商 (`Provider`) 区分？ |
| 3 | `handler/subscription_handler.go` → `PurchaseSubscription` | 用户购买套餐时，数据是如何写入 `user_subscriptions` 和 `redeem_codes` 的？ |
| 4 | `handler/gateway_handler.go` → 计费部分 | 在处理 API 请求时，是检查 `user_subscriptions` 的配额，还是直接扣用户余额？ |

### 验证目标
- [ ] 确认 `user_subscriptions` 缺少 Nexus PRD 中描述的"订阅实例"概念
- [ ] 确认 Sub2API 的订阅是直接与 `User` 或 `Group` 关联，而不是与 `Provider` 关联
- [ ] 理解 Sub2API 的"订阅扣费"和"按量扣费"是如何在计费逻辑中分流的（如果存在的话）

## 问题三：`abilities` 权限体系有没有任何替代品？

### 核心疑问
Sub2API 没有 `abilities` 表，那么它是如何控制"谁 (Group) 能用哪个供应商 (Provider)" 的？还是没有任何控制？

### 源码追踪路径

| 步骤 | 追踪文件 | 要回答的问题 |
|------|---------|-------------|
| 1 | `ent/schema/account_group.go` | 这张中间表是如何关联 `Account` 和 `Group` 的？是不是只要关联了，该 Group 下的用户就能用？ |
| 2 | `handler/gateway_handler.go` → `SelectAccount` 或权限检查部分 | 在选择 `Account` 之前，有没有一段代码是校验"当前用户所在的 Group 是否有权使用这个 `Account`"？ |
| 3 | `handler/admin/group_handler.go` | 在创建/编辑 Group 时，有没有地方可以设置"可用账号"的范围？ |

### 验证目标
- [ ] 确认 Sub2API 的权限控制**仅停留在**"Account 是否分配给 Group"
- [ ] 确认 Sub2API **没有**进一步的"供应商级别"的权限开关
- [ ] 理解 `account_group` 表的作用，为后续设计 `abilities` 表提供参考

## 问题四：熔断有没有替代机制？

### 核心疑问
Sub2API 明确没有独立的熔断逻辑，那 `channel_monitors` 到底做了什么？网关在选择账号时，会参考它的状态吗？

### 源码追踪路径

| 步骤 | 追踪文件 | 要回答的问题 |
|------|---------|-------------|
| 1 | `handler/admin/channel_monitor_handler.go` | `ChannelMonitor` 的 CRUD 逻辑，它监控什么？如何定义"正常"和"异常"？ |
| 2 | `service/channel_monitor_service.go` | 监控服务的核心逻辑：它是定时轮询还是被动探测？失败/成功是如何计数的？ |
| 3 | `handler/gateway_handler.go` → `SelectAccount` | **最关键的一步**：在选择 `Account` 时，是否查询了 `ChannelMonitor` 的状态？如果状态是 `error`，是否会跳过这个 `Account`？ |
| 4 | `handler/failover_loop.go` | 文件名看起来像故障转移，它的具体逻辑是什么？ |

### 验证目标
- [ ] 确认 `ChannelMonitor` 是一个**监控工具**，提供了状态数据
- [ ] 确认在路由选择 (`SelectAccount`) 时，**是否会**利用监控状态来排除不健康的节点
- [ ] 如果 `SelectAccount` 没有排除故障节点的逻辑，那么 Sub2API 的容错就完全是"靠重试"，而不是"靠熔断"
